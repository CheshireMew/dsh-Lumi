# Agent Note: 开发阶段验证预算

Status: implemented

[English](2026-08-16-development-stage-verification.md) | 中文

## 问题

这个预发布仓库把逐文件全量覆盖率、完整应用矩阵、发布检查和远端 CI 完成当成普通实施证据。大范围改动因此会在代码和范围尚未稳定时启动昂贵验证，随后又发现另一项问题，使同一套全量结果多次失效。这些检查通过只能证明被测修订，不能证明尚未完成的产品已经完成。

## 决定

活跃开发只在当前主机验证一个逻辑改动批次。验证阶段先读取一次公开 CI 中最近可用的已完成失败，并把相关证据归类为产品、测试基础设施或环境失败。普通实施任务不监控排队或运行中的远端作业。非强制推送成功后任务立即结束并把远端检查报告为异步状态；其它平台或持续监控 CI 需要用户明确要求。

聚焦 spec 和能够证明结果的最窄类型、构建、文档或冒烟消费者是常规开发检查。全量覆盖率、完整快照和 Electron E2E、真实 API、视觉与性能矩阵、打包、签名、发布和非本机平台检查属于里程碑证据，只在代码冻结、发布候选、用户明确要求，或聚焦失败证明存在系统性影响时运行。预计超过 15 分钟的检查会在开始前说明命令、目的和时间估计。

公开 `test:coverage` 命令与 CI 共同使用覆盖率门禁执行器。插桩源码测试与不提供独有阈值证据的编译器或子进程重型套件并行运行。在 Node 22 的 Windows 环境中，普通 fork 隔离测试使用两个 worker，明确的进程敏感清单仍在顺序有界分片中保持单 worker。这样退出全局单 worker 限制，同时不会重新进入 Node 24 的 worker thread 路径。

## 验证

门禁执行器和单元测试调用规划 spec 保护现有通道与分片身份。一个聚焦代表性分片在固定 Node 运行时下比较 Windows worker 预算；文档和 Agent Note 检查覆盖长期开发合同。本次改动的本地完成证据有意不包含全量覆盖率。

## 考虑过的替代方案

**每次改动都运行完整仓库。** 否决：同一任务继续修改时，全量结果会反复失效，而且多数小改动不会影响全部消费者。

**移除 100% 覆盖率策略。** 否决：该策略在里程碑和 CI 中仍有价值；问题在运行频率和执行入口，不在阈值本身。

**推送后等待每一项远端作业。** 否决：公共 runner 拥有异步验证。普通实施只报告已经排队的证据并释放任务，不把 CI 延迟变成开发墙钟时间。

## 后果

小改动在取得聚焦本地证据后结束，仓库级检查只在明确稳定边界运行一次。远端失败会在下一次验证阶段继续可见，但不会占住发起它的任务。里程碑和发布声明仍需要各自命名的证据，未完成的功能开发不再自动继承这些声明。
